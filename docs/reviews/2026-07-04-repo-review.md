## Summary

The repo's release engineering, tarball hygiene, and silent-failure discipline are well above standard for a solo library. The problems cluster in four themes:

1. The shipped stylesheet leaks into consumer apps — unprefixed, unlayered token variables collide with Tailwind v4's own theme names (the one Critical finding)
2. Several quality gates are silent no-ops right now — the exact failure class CLAUDE.md warns about (dead `unit` test project, unreferenced `vitest.shims.d.ts`, unwired coverage, dead `--color-ring` contract variable, un-gated component CSS imports)
3. The release path trusts but never re-verifies — publish runs no tests, no `prepublishOnly` guard, third-party actions tag-pinned in jobs holding publish rights
4. Doc drift despite the update protocol — README's override contract is incomplete, ARCHITECTURE claims tests that don't exist, CLAUDE.md's "three docs" and "engines enforces the floor" claims are now false

## Critical

### C1. Published CSS silently overrides consumer Tailwind theme variables

`dist/styles.css:124-156` emits the library's primitives in an unlayered `:where(:root)` block under Tailwind's own reserved names: `--color-blue-500`, `--color-blue-600`, `--color-gray-100`, `--radius-sm/md/lg`, the whole `--spacing-*` scale. A consuming Tailwind v4 app keeps its theme variables in `@layer theme`; unlayered declarations beat layered ones regardless of specificity, so importing this stylesheet hue-shifts the consumer's `text-blue-600` (library `oklch(0.50 0.19 256)` vs Tailwind default `oklch(54.6% 0.245 262.881)`) and changes every `rounded-md` in their app from 6px to 8px. The file even ships both conflicting definitions (Tailwind defaults at lines 5–12, library values at 124+). The `:where()` zero-specificity trick defends against specificity wars, not layer order.

Two adjacent consequences:

- The idiomatic Tailwind override path fails silently: a consumer theming via `@theme { --color-primary: … }` compiles into `@layer theme`, which loses to the library's unlayered block. Only the plain `:root { … }` form shown in `README.md:50-59` works, and nothing documents that
- `--spacing-1: 8px` reuses Tailwind's name with different semantics (Tailwind's `1` is universally 4px), maximizing confusion for exactly the consumers most likely to install this

Fix: prefix every variable the library owns in the Style Dictionary output (`--ui-color-blue-600`, `--ui-radius-md`), keeping at most the deliberate semantic override surface unprefixed — this is what MUI (`--mui-*`) and Mantine (`--mantine-*`) do. CLAUDE.md's rejection of Tailwind `prefix(tw)` was correct but solved a different problem; nothing prevents prefixing in `tokens.json` or the SD config. This is a breaking change to the override contract, so it's cheapest now, pre-1.0, with one component.

## Important — styling and token architecture

### S1. `@theme inline` output maps every variable onto itself

`dist/styles.css:13-36` contains `--color-primary: var(--color-primary)`, `--radius-md: var(--radius-md)`, etc. inside `@layer theme { :root, :host }`, generated by `style-dictionary.config.mjs:60-72`. It only behaves because the unlayered token block out-cascades it. Inside a shadow root, the `:host` self-reference is the only declaration in scope — a guaranteed cycle, invalid at computed-value time, components unstyled. It's also dead weight: no Tailwind utility (`bg-primary`, `p-2`) is used anywhere in components (`variants.ts` emits only `ui-*` literals), so the entire `@theme` registration serves nothing. Aligns with the already-planned Tailwind-to-vanilla-CSS migration noted in `ARCHITECTURE.md`; the C1 prefixing fix dissolves this too.

### S2. Component state styles are unlayered, breaking the stated override model

`button.css`'s `@utility` blocks land in `@layer utilities` (`dist/styles.css:38-123`), but every state rule — `:hover`, `:active`, `:focus-visible`, `:disabled`, `::after` ripple, `[data-theme='dark']` overrides, all media queries — ships as plain unlayered CSS (`dist/styles.css:168-267`). The file header promises "predictable low-specificity overrides", but unlayered library rules outrank all consumer layered CSS: a consumer's `hover:bg-*` utility can never beat `.ui-btn-primary:hover:not(:disabled)` without unlayered CSS or `!important`. Fix: wrap all component CSS, states included, in one named library layer (e.g. `@layer ui`) declared so consumer layers sit above it.

### S3. `--color-ring` is documented but consumed by nothing

`README.md:44` sells it as "Focus ring on every intent"; grep finds zero references in any component CSS — focus-visible uses a transparent outline plus a box-shadow elevation bump. A consumer overriding it sees no effect. Either wire it into `:focus-visible` (shadow-only focus indication is also weak for WCAG focus-appearance) or remove it from the contract.

### S4. Token tiering stops at color/spacing/radius

Elevation, typography, and motion are hardcoded per component: `button.css` embeds `rgba(0,0,0,…)` shadows (wrong on dark surfaces), fixed `32/36/42px` heights, font sizes and weight, `200ms`/`350ms` durations, and hover/active lightness deltas. None of this is reachable through the override contract, and at 10+ components these values drift per file. Add `--ui-shadow-*`, type-scale, and duration tokens to the semantic tier before component #2 or #3 sets the copy-paste template.

### S5. Component CSS registration is a manual `@import` with no gate

`src/styles/index.css` instructs "add one @import line per new component"; forgetting it ships the component unstyled while every gate stays green (unknown `ui-*` classes emit nothing, Tailwind doesn't error). The repo already asserts against the analogous token gap (`assert-theme-parity.mjs`) — add a sibling assertion that every `src/components/*/*.css` is imported.

## Important — packaging and release

### P1. Main export has no `default` condition

`package.json`'s `"."` export exposes only `types` + `import`. Node ≥22.12 supports `require()` of ESM — the very floor `engines.node` targets — but without a `default` condition a CJS consumer gets `ERR_PACKAGE_PATH_NOT_EXPORTED`. Standard 2026 shape for ESM-only: `{ "types": …, "default": "./dist/index.mjs" }`. Also add the zero-cost `"./package.json": "./package.json"` subpath for introspecting tools.

### P2. Nothing guards against a stale or unverified publish

Two related gaps:

- No `prepublishOnly`/`prepack` hook — a manual `pnpm publish` ships whatever `dist/` is on disk
- `release.yml` publishes without re-running any gate: push to `main` triggers CI and release concurrently, and `pnpm release` is `build && changeset publish` — no tests, no `verify:pack`, no `assert:use-client`. Branch protection (`strict: true`) means merged code was green pre-merge, so this is mitigated, but the publish artifact itself is never re-verified

Fix: `"prepublishOnly": "pnpm verify:pack && pnpm assert:use-client"` (build is already in `release`), and consider gating the release job on the CI run.

### P3. Third-party actions pinned by mutable tag; `chromaui/action@latest` is the worst case

`chromaui/action@latest` floats entirely, in a job holding `CHROMATIC_PROJECT_TOKEN`. `changesets/action@v1` and `actions/create-github-app-token@v3` are major-tag pins in the release job, which has `id-token: write` (npm trusted publishing) and an App token with contents+PR write — a hijacked tag could publish to npm. Pin third-party actions to full commit SHAs; the already-configured Dependabot `github-actions` ecosystem updates SHA pins fine.

## Important — CI and automation

### A1. Dependabot npm PRs are failing right now, with no mitigation in config

Today's runs on the grouped npm bump branch fail in ~20s at `pnpm install --frozen-lockfile` with `ERR_PNPM_OUTDATED_LOCKFILE` — the known pnpm `catalog:` regeneration gap (react, react-dom, typescript, tailwindcss are `catalog:`). CLAUDE.md documents the manual fix, but `dependabot.yml` does nothing about it, so every weekly grouped bump touching a catalog dep lands red. Options: switch npm updates to Renovate (native pnpm-catalog support), `ignore` the four catalog deps in Dependabot and bump them manually, or automate the `pnpm install` fixup on `dependabot/**` branches.

### A2. Every commit runs CI — and a billed Chromatic snapshot — twice

`ci.yml` triggers on both `pull_request` and `push: branches: ['**']`; the concurrency group keys on `github.ref`, which differs between the push ref and the PR merge ref, so both run to completion (confirmed in run history). Doubles Actions minutes and Chromatic snapshot quota. Fix: `push: branches: [main]` plus bare `pull_request`.

### A3. Chromatic is a required branch-protection check that can never pass on fork PRs

`secrets.CHROMATIC_PROJECT_TOKEN` is empty on fork `pull_request` runs, and branch protection requires the `chromatic` context — so any external contribution to this public repo is permanently unmergeable. Gate the job on non-fork PRs and drop it from required checks, or adopt Chromatic's documented fork-PR pattern.

### A4. `ci.yml` has no `permissions` block

Currently safe because the repo default is read-only, but that safety is one settings flip away from gone. `release.yml` does it correctly; add `permissions: contents: read` to `ci.yml`.

## Important — quality gates that are silently inert

These are instances of the exact "green build, silent no-op" failure class CLAUDE.md documents:

### G1. The `unit` Vitest project matches zero files, and ARCHITECTURE claims tests that don't exist

`vitest.config.ts`'s node-environment project includes `src/**/*.test.ts`; no `*.test.*` file has ever existed (verified against `git log --all`). `vitest run` passes because the storybook project has tests, so the empty project is invisible. Meanwhile `ARCHITECTURE.md` lists `*.test.ts` in the file map and describes the unit project as running "pure-logic unit tests". Either write the `buttonClasses()` unit test the docs describe, or fix the docs and remove the project until a first test lands. Also widen the glob to `*.test.{ts,tsx}` when it does — a future `.test.tsx` is currently picked up by neither project.

### G2. `vitest.shims.d.ts` is loaded by no TS program

It carries the `@vitest/browser-playwright` type reference, but neither tsconfig includes it and nothing references it (verified). Browser-mode types don't resolve in the editor/typecheck as intended. Add it to `tsconfig.json` include or delete it.

### G3. Root config files are never type-checked

`eslint.config.ts`, `vitest.config.ts`, `tsdown.config.ts` are in neither tsconfig include; a type error there surfaces only as a runtime load failure. Standard: a `tsconfig.node.json` (or added include) covering root `*.config.ts`, folded into `pnpm typecheck`.

### G4. Coverage is installed but never wired

`@vitest/coverage-v8` is a devDependency, the eslint ignores even anticipate a `coverage/` dir, but no `coverage` block, no `--coverage` flag, no threshold exists anywhere. Wire it with thresholds in CI, or drop the dependency — right now it's an implied gate that doesn't exist.

### G5. The attw re-enable trigger has plausibly already fired

CLAUDE.md and ARCHITECTURE say `verify:types` is out of CI "until upstream ships a fix" for attw 0.18.2 — but `package.json` now carries `^0.18.3`. Nobody re-tested. Re-run `pnpm verify:types` (and the `zod` control test); either re-gate in CI or update the trigger. Until then, nothing checks `node10`/`node16` resolution modes — which relates directly to P1's missing `default` condition being an unverified tradeoff.

## Important — cross-doc contradictions

### D1. `engines.node` contradicts the documented build floor (flagged independently by three agents)

`package.json` says `>=22.12.0`; CLAUDE.md says tsdown needs ≥24.11.1 _and claims "`engines.node` enforces the floor"_ — it doesn't. With `engineStrict: true`, a contributor on Node 22.12–24.10 passes install and then hits the cryptic `Unexpected module status 3` failure the gotcha exists to prevent. The 22.12 floor is deliberately right-sized for consumers, so the fix is either `devEngines.runtime` for the contributor floor, or correcting the gotcha to point at `.nvmrc` as the real enforcement.

### D2. README omits part of the public override surface

`ARCHITECTURE.md` declares `--spacing-*` and `--radius-*` public override surface alongside the color variables; `README.md`'s theming section — the consumer-facing contract — documents only the nine color variables. A semver-stable API surface undocumented to consumers is drift in the one doc whose job is that contract. (Also undocumented: overriding a light-theme variable at `:root` specificity beats the `:where([data-theme="dark"])` rebinding, freezing that token in both themes — the contract should state overrides must be paired.)

### D3. CLAUDE.md's "three docs persist long-term" is now false

The uncommitted branch adds `docs/workflow.md` as a fourth persistent doc, but CLAUDE.md's Documentation section (ownership table, re-read protocol) wasn't updated and `ARCHITECTURE.md`'s "See Also" landscape omits it. This is the drift the update protocol exists to catch — worth fixing before this branch merges.

### D4. ARCHITECTURE file-map drift

The file map omits `button.css` (despite the styling section mandating co-located CSS), `scripts/assert-theme-parity.mjs`, `scripts/assert-pack-contents.mjs` (while listing the third script), `.storybook/modes.ts`, and `docs/workflow.md`; the `files` summary oversimplifies the actual negated globs; the invariants section still says "while at `0.0.0`" at version 0.3.0.

## Minor

Styling and tokens:

- Two dark-mode mechanisms coexist: `@custom-variant dark` is declared but never used; `button.css` uses raw `[data-theme='dark']` descendant selectors instead — at specificity (0,2,0) and unlayered, so dark-state styles are the hardest thing in the system for consumers to beat
- Semantic naming is inconsistent (`--color-primary` implies background, `--color-neutral-bg` is explicit) — pick one scheme (`X-bg/X-fg/X-border` or shadcn's `X`/`X-foreground`) before more components lock it in as semver surface
- Fixed px button heights with rem font sizes risk label clipping under text-only zoom (WCAG 1.4.4) — prefer `min-height`
- Dark token build disables all SD warnings to silence one expected one (`log: { warnings: 'disabled' }`) — future genuine warnings are also suppressed
- `mergeSets` flattens `core`/`light`/`dark` into one namespace with no collision guard — a future semantic named like a primitive silently clobbers it
- Dark theme never sets `color-scheme: dark`, so consumer form controls and scrollbars stay light under `[data-theme="dark"]`
- `dist/styles.css` ships unminified, and there's no `pnpm css --watch` for the Storybook dev loop (editing `button.css` requires a manual rebuild to see changes)

Packaging and CI:

- `tsdown.config.ts` pre-lists radix-ui packages in `neverBundle` that are neither dependencies nor peers — if a future component imports radix, the published package ships an import of an undeclared dependency; remove until adopted (with a named trigger) per the repo's own deferral rule
- Release job omits `cache: pnpm`; Playwright chromium re-downloads every CI run (~30–60s); no `timeout-minutes` on any job
- "Allow GitHub Actions to create and approve pull requests" is enabled but unused (the App token opens the Version PR) — disable it
- `.changeset/config.json` schema pin (`3.1.1`) will drift from the installed validator over time
- `package.json` lacks `keywords` and `author`; `description` is too generic for npm search; README has no badges and shows only `pnpm add`

Tooling config:

- `eslint .` with `import-x/order: 'warn'` means warnings never fail CI — use `--max-warnings 0` or promote to `error`
- `.storybook/**` gets only `tseslint.recommended` — no react-hooks/jsx-a11y/type-aware rules on files that define React decorators
- No `eslint-config-prettier`, no pre-commit hooks, no `.editorconfig` — all enforcement is CI-side (acceptable solo, but a red `pnpm format` is only discovered after push)
- `lib: ES2023` vs `target: ES2022` lets code type-check against APIs tsdown won't down-compile; strictness lacks `noUnusedLocals`, `exactOptionalPropertyTypes`, `noImplicitOverride` vs the `@tsconfig/strictest` bar
- `cspell` covers only `README.md`, `tokens/README.md`, `src/**` — ARCHITECTURE.md, CLAUDE.md, and `docs/` (the heaviest prose) are unchecked

Hygiene:

- `.gitignore` lacks `.env*`; `.claude/settings.local.json` is ignored only via the author's personal global gitignore — any other clone sees it as committable (and `.prettierignore`'s comment claiming `.claude/` is gitignored is wrong)
- Version-stamped comments in `.storybook/main.ts` and `preview.tsx` ("10.4.1" vs installed ^10.4.4) violate doc rule 5
- App-token release rationale is duplicated in prose in both `ARCHITECTURE.md` and `docs/workflow.md` (the `release.yml` comment copy is fine) — two prose copies will drift
- New deviation-log entry misattributes `--force` to `pnpm pack` (it belongs to `npm install`; `docs/workflow.md` gets it right)
- No SECURITY.md — the one community file worth adding for a published npm package (CONTRIBUTING/CODE_OF_CONDUCT are proportionately skippable solo)

## Notes and accepted tradeoffs

- Single monolithic stylesheet is standard and fine at this scale; the co-located per-component CSS makes a later per-component split cheap (~30+ components)
- Chromium-only test matrix is common and defensible
- Dark-theme a11y coverage relies on hand-authored `Dark*` stories per component — has a named trigger (component #3), compliant with repo rules, but it's a forget-one-story silent gap until then
- Running Style Dictionary as a script rather than the CLI is unconventional but valid v5 API usage
- `sideEffects` second entry is redundant (glob covers it) — harmless

## Done unusually well

- Release engineering: npm OIDC trusted publishing with provenance, no stored token, and the App-token Version PR correctly solving the required-checks trap — with the why documented in place
- Tarball hygiene beyond standard: `files` whitelist + `assert-pack-contents.mjs` walking the actual tarball + publint
- RSC/React Compiler handling (`babel-plugin-react-compiler` precompile gated by `assert-use-client.mjs`) is more rigorous than almost any published component library
- Tree-shaking/DX pairing: preserve-modules ESM, CSS-only `sideEffects`, sourcemaps resolving into shipped `src/` so go-to-definition lands on real TypeScript
- Silent-failure discipline where it exists is excellent: typed literal class-maps forcing static CSS emission, `assert-theme-parity.mjs`, the a11y gate proven failing-by-default with a seeded violation — the G-series findings above are gaps in an otherwise strong pattern, which is exactly why they stand out
